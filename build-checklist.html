Raspberry Pi · 64×32 HUB75

Scoreboard Build Runbook

Blank microSD card to a board someone else can plug in at their house and set up from a phone. Build the first one from scratch, then clone it: the second unit should take ten minutes, not an hour. Every unit gets built on your wifi first, then reset for handoff.

~1 hr first unit ~10 min per clone 0 commands typed on the Pi Pi OS Lite + Comitup No reliance on Imager customisation
0 / 0

Two routes. Pick before you start.

First unit Build from a blank card

Phases 01 to 06 below. The card carries its own installer and the Pi sets itself up. Budget an hour, and expect to be in the terminal.

Units 2, 3, 4 Clone the working unit

Skip to phase 07, then set up remote updates before the card goes out the door. Writing a known-good image takes about ten minutes and bypasses every step that can fail: no apt, no compiling the LED driver, no cloud-init, no package repositories. If you have a golden image, this is not the shortcut, it is the route.

01

Gather

One supply runs everything. Power goes into the Bonnet's barrel jack, which feeds the panel and back-powers the Pi through an onboard 1 A diode. Never feed the panel through the Pi's 5 V pins.

Chaining a second panel needs a bigger supply, not just a cable. Panels are rated near 4 A each at 5 V, measured at full white across every pixel. A scoreboard is mostly black so the real draw is closer to 1–2 A, but the peak is what the supply has to survive, and a scoreboard hits white often: a snow screen, a team in white, a flash on a score change. Two panels plus a Pi on a 4 A supply browns out on those frames, and a brownout on a HUB75 panel does not look like a power problem. It looks like corrupt rows, wrong colours and random flicker, which is exactly what you would otherwise spend a week blaming on GPIO timing. Budget 5 V 8 A for two panels, 10 A if you want headroom, and set matrix.chain_length to 2.
02

Flash the card

Imager is supposed to write your wifi and login onto the card before first boot, which is what means you never have to reach an unconfigured board. It does not always manage it, and it does not tell you when it fails, so this phase ends by checking rather than assuming.

The three mechanisms do not read each other's files. Pi OS moved to cloud-init in the Trixie images, and a custom.toml on one of those is simply ignored. The giveaway is that it stays on the card: a file that was actually consumed is deleted during the boot that read it. Phase 03 detects which format the card wants and writes that one.
Empty output is also common, and not your mistake. Imager has a known intermittent bug where the settings are entered, the write reports success, and nothing reaches the card, traced to the files not being flushed before eject. Reported against 2.0.6 and fixed later, so update Imager, but the failure is silent when it happens. Phase 03 writes the settings itself, which is why this is a check rather than a stopping point.

03

Load the card

The Pi's Linux partition is ext4 and macOS cannot touch it. The small partition Finder shows as bootfs is plain FAT32, and Pi OS runs a script from it on the very first boot. That is the whole trick: the board installs itself, and you never open a terminal on the Pi.

On your Mac, card still inserted
cd ~/Downloads
unzip -o led-scoreboard-v2.28.zip 'scoreboard/boot/*'
chmod +x scoreboard/boot/prepare-sd-card.sh

scoreboard/boot/prepare-sd-card.sh ~/Downloads/led-scoreboard-v2.28.zip \
  --name "Living Room Scoreboard" \
  --panels 1 \
  --wifi "YourNetwork" --wifi-pass "…" \
  --user yourname --user-pass "…"
Those last two lines replace Imager's gear screen. They write whichever format the card wants — cloud-init's three files on a Trixie image, custom.toml on an older one — detected from cmdline.txt. Same files Imager would have produced, written once and checked rather than left to the race that drops them. They also always switch SSH on and grant the account passwordless sudo: the installer needs both, and neither is obvious by its absence. A board that joins the wifi and answers to its name but refuses every login looks like a far deeper problem than a missed checkbox.
Passing them wins over Imager. Anything Imager left on the card is moved aside to custom.toml.imager-bak rather than deleted. Leave the options off and Imager's settings stand untouched.
The login password sits on the card. It is hashed if your openssl can, plain text if it cannot, and the script tells you which. The wifi password is always plain, because the encrypted form is reported not to apply reliably. This is a FAT partition, so file permissions do not exist there. Delete custom.toml from the card after the first boot if that bothers you.
Nothing gets dragged into the card by hand. The script copies the zip, the first-boot script and the name onto bootfs itself, and prints ok zip copied when they land. Leave the release in ~/Downloads and point at it: the first path on that last line is the script you are running, the second is the file you are feeding it, and neither one needs to be on the card already.
Give every board its own name. Two boards both called Scoreboard both want scoreboard.local, and on the same network one of them loses. Name them for whoever is getting them.
It handles both kinds of card. If Imager wrote its own first-run script, this rides along inside it and leaves cmdline.txt untouched. If not, it claims the boot hook itself and backs up the original. Running it twice on the same card is safe.
04

First boot, hands off

Two boots, deliberately. The first-boot hook runs in a stripped-down systemd target with no networking, which is fine for copying a file off the card and far too early to fetch packages. So it arms the installer and reboots; the second boot has a real network stack and does the work.

The log lives on the card. If nothing happens, put the card back in the Mac and open scoreboard-install.log on bootfs. With no screen, no keyboard and no ssh, that is the only diagnostic there is, which is exactly why it is written there.
Wifi is the one hard requirement. The matrix driver compiles from source, so the first boot needs internet. If Imager's wireless settings were wrong or missing, the log says so and nothing is lost: the payload is already on the Pi, so fix the wifi, ssh in, and run ~/scoreboard/install.sh --yes.
Doing it over ssh instead

For a board that is already up, or when you would rather watch the installer run.

On the board, to get the account name and address
whoami; hostname -I

Do not assume pi and scoreboard.local. The account is whatever the card was prepared with, and the .local name only works if mDNS came up. The IP always works.

From your Mac
scp ~/Downloads/led-scoreboard-v2.28.zip <user>@<ip>:~
Over SSH, one command
unzip -o led-scoreboard-v2.28.zip && cd scoreboard && ./install.sh --yes

A failed step does not kill the run: everything that failed is listed at the end with its fix, and the installer is safe to re-run. Drop --yes to be asked about Comitup.

05

Test and tune

Everything you settle here is a thing you do not have to talk a brother through over the phone in November.

On the Pi
./scoreboard doctor
./scoreboard status
./scoreboard logs     # ctrl-C to stop watching
Leave the panel settings correct. The handoff reset deliberately keeps them, because the person receiving the board has no way to work out that their panel needs multiplexing 3.
06

Prepare for handoff

This forgets your wifi so Comitup falls back to access-point mode in their house, resets the setup wizard, and clears the SSH host keys and machine-id so cloned cards do not collide on the same network.

On the Pi, last thing
cd ~/scoreboard
./scoreboard prepare
sudo shutdown -h now
Do not boot this card on your wifi again. It would re-save your network, and Comitup only opens its access point when there is nothing left to connect to. If you do, re-run the prep script.
07

Clone for the remaining units

A clone is byte-for-byte identical to the unit it came from, which is the point and also the catch: it arrives with the same hostname, the same SSH host keys and the same machine-id. Two of those on one network collide, so each clone gets an identity before it meets the original.

1. On your Mac, from the shut-down card
diskutil list                        # find the card by SIZE, not by number
diskutil unmountDisk /dev/disk4
sudo dd if=/dev/rdisk4 of=~/scoreboard-golden.img bs=4m status=progress
Check the identifier against the size before running dd. It writes to whatever you point it at, including your own disk. Note rdisk4 rather than disk4 in the dd line: the raw device is several times faster.
2. On the clone, first boot, original powered off
ssh scoreboard@rgb-scoreboard.local

# New machine-id and SSH host keys, so DHCP and ssh stop seeing twins
sudo rm -f /etc/machine-id /var/lib/dbus/machine-id
sudo systemd-machine-id-setup
sudo rm -f /etc/ssh/ssh_host_*
sudo ssh-keygen -A

# New name. This also sets the hostname on the next boot.
cd ~/scoreboard
echo "Kitchen Scoreboard" > state/preseed-name.txt
./install.sh --yes --no-comitup

sudo reboot
Your Mac will refuse to connect after that, and it is right to: the host key changed, which is exactly what a man-in-the-middle looks like. Clear the old entry and reconnect at the new name.
On your Mac
ssh-keygen -R rgb-scoreboard.local
ssh scoreboard@kitchen-scoreboard.local
Why not set the name from the Mac? The name lives on the Linux partition, which macOS cannot write. The boot partition trick only applies to a first-boot install, and a clone has already had its first boot.
3. Per unit, when it is ready to go out
./install.sh --comitup       # the wifi portal, only needed for a gift
./scoreboard prepare         # forget your wifi, reset the wizard
sudo shutdown -h now
Order matters. Comitup has to be installed while the board still has your network, because installing it needs one. The reset comes after.
08

Update a board already in service

Once four boards exist this is the only step you keep doing. It does not touch the card, the wifi or the account: the release lands in the home folder, the installer overwrites the project and restarts the service, and settings, teams and ZIP code survive because they live in config.json, which is left alone.

From your Mac
scp ~/Downloads/led-scoreboard-v2.28.zip <user>@<board>:~
Then, over SSH on the board
cd ~ && unzip -o "$(ls -t led-scoreboard-*.zip | head -1)" && cd scoreboard && ./install.sh --yes
That line deliberately does not name a version. ls -t | head -1 picks whichever release you most recently copied over, so the filename in the unzip can never drift out of step with the filename in the scp — which is its own small class of wasted evening: unzipping a version you did not send, watching the install succeed, and finding the old code still running.
Confirm, on the board
grep -m1 VERSION ~/scoreboard/main.py
./scoreboard status
An upgrade clears the logo cache. Cached bitmaps otherwise outlive every fix to the artwork pipeline, so a release that corrects how a logo is drawn would appear to change nothing. Nothing else is discarded.
09

Set up remote updates

Do this once, before you build the gift cards. After it, a release you publish reaches all four boards overnight without you being on anyone's network. Boards ask outward over ordinary HTTPS, so nothing is forwarded, nothing listens, and nothing is configured on anyone's router — it works behind carrier-grade NAT, where inbound would not.

Once, on your Mac
./tools/release.sh --init-key ~/.scoreboard/release-key.pem
That file is the only thing standing between a stranger and four Pis inside three houses. Whoever holds it can make every board run whatever they like, at four in the morning, with no one watching. Keep it off the boards, out of the repo, and backed up. The public half ships in the release and gets copied to /etc/scoreboard/update-key.pem on first install, where an update cannot reach it — which is the point: a release can never replace the key that would have caught it.
Publishing a release
./tools/release.sh beta

Builds the zip, runs the tests, hashes it, points the beta channel at it, signs the manifest, uploads the asset and pushes. Your board picks it up that night, or immediately with ./scoreboard selfupdate --force.

Once yours has run it for a day
./tools/release.sh stable --promote
The two channels are the actual safety feature. Signing stops an attacker, which is unlikely; the promote step stops you, which is not. Nothing reaches the three boards you cannot touch until a release has spent a day running on the one you can.

What a board does at 4am, in order. Waits for the clock to be right, because a Pi with no battery clock cannot judge a certificate or a quiet hour. Fetches the manifest and its signature and verifies it against the key in /etc; a manifest that does not verify ends the run. Compares versions and stops if there is nothing new. Stops if any game is live, because nobody wants the panel to reboot during a drive. Downloads, checks the hash against the signed manifest, unpacks into a staging directory beside the running install and runs that release's own test suite there — the panel is still showing scores throughout. Only if all of that passes does it back up the working copy, swap the new tree in, restart, and wait for the service to report the expected version on its own port. Anything that fails restores the backup, restarts, and writes the bad version to a list it will not retry.
Settings survive. config.json, state/ and the logo cache are not in the release archive and are copied across explicitly as well, so teams, ZIP code and panel tuning are never touched by an update. The logo cache is deliberately cleared, because a cached bitmap outlives a fix to the artwork pipeline.
→

What they do

The whole reason for the steps above. No terminal, no cable, no phone call to you.

  1. Plug the board in and wait about a minute.
  2. On a phone, join the wifi network named scoreboard-nnn.
  3. The setup page opens by itself. Pick the home wifi, enter the password.
  4. The board reboots onto their network.
  5. Its own wizard asks for a board name, a ZIP code, and their teams.
  6. It finishes by showing the address to bookmark, like mikes-board.local:8080.

Tell them it updates itself. Once a night the board checks whether you have published a new version and installs it if so, which is why they will never need to do anything about a bug. It is their board, so say it out loud rather than leaving them to find it: the page they just bookmarked has an Updates section showing the version it is running, when it last checked, and a switch to stop it. Nothing about their network or their viewing leaves the house — the board asks for a file and hangs up.

When something goes wrong

SymptomCause and fix
Panel never lights after a card install Put the card back in the Mac and read scoreboard-install.log on bootfs. It names the step that failed. Most often it is no network after 5 minutes, meaning Imager's wifi was wrong: fix it, ssh in, and run ~/scoreboard/install.sh --yes. The payload is already on the Pi, so nothing is lost.
zsh: no such file or directory running the prep script The script is not where the command says it is. ~/ is only shorthand for your home folder, so ~/Downloads/prepare-sd-card.sh is /Users/you/Downloads/prepare-sd-card.sh and zsh is reporting that no such file exists. Rather than hunting for a stray download, take it out of the zip as shown in phase 03.
macOS refuses to run the script A file downloaded through a browser is quarantined. Run it as an argument to bash instead: bash scoreboard/boot/prepare-sd-card.sh ...
Prep script says the card has no wifi and no user account Either Imager's intermittent bug, or an older build of the script looking for the wrong files. Nothing was written to the card, so just pass --wifi, --wifi-pass, --user, --user-pass and re-run.
custom.toml still on the card after a boot It was never read. A consumed customisation file is deleted by the boot that applies it, so a file still sitting there means the image wanted a different format — almost always cloud-init on a Trixie image. Re-prepare the card with the current script and re-flash.
Log shows stage A only, nothing from stage B On builds before v2.10 every stage B log line went through sudo, so a sudo prompt erased the entire log and looked identical to a service that never started. Update and re-prepare.
Log says target user: with an account you did not ask for Also pre-v2.10. Stage A resolved uid 1000 before cloud-init had created the real account, so it installed for the image's placeholder. Stage B now resolves the account, after cloud-init has run.
Install log shows sqv returned an error code or Not live until The Pi’s clock is wrong, not the repository. A Pi has no battery-backed clock, so on first boot the date is whatever was last written to disk, and apt refuses a signature whose validity has not started yet as far as this board is concerned. The confusing part is that HTTPS keeps working throughout, because a certificate’s window is months wide and a day of drift fits inside it. Also note apt-get update exits 0 when this happens: it prints warnings, falls back to the previous index and calls it success, so an install can continue on package lists days out of date. From v2.22 stage B waits for NTP before starting and the installer detects this, waits for sync and retries.
Install seems to stop partway through the log Most often it had not finished. The install is 10 to 20 minutes on a Pi 3 A+, most of it compiling the matrix bindings, and stage B allows itself an hour. Check the last line: a step in progress means it was interrupted, an ERROR line means it failed. Do not pull the card mid-install, which risks corrupting the filesystem. Nothing needs re-flashing either way — the setup service stays enabled until it succeeds, so putting the card back and powering on re-runs the install from the payload already on the Pi.
Log says no network after 5 minutes but the board is on your wifi Builds before v2.17 could never pass their own connectivity check. The probe used curl -f, which treats any HTTP status of 400 or above as a failure, and files.pythonhosted.org answers 404 to a bare GET because it serves package files and has no root page. So stage B waited out its full timeout on a perfectly healthy network and then advised checking the wifi. Nothing is lost when this happens: the payload is already on the Pi. Recover without re-flashing with cd ~ && unzip -o /var/lib/scoreboard/payload.zip && cd scoreboard && ./install.sh --yes, and update to v2.17 before preparing any more cards.
Card prep cannot find the boot volume The card is not mounted, or Finder named it something other than bootfs. Pass it: --volume /Volumes/<name>.
Pi reboots over and over The first-boot hook did not clear itself from cmdline.txt, which asks for a reboot on success. Mount the card and delete everything from systemd.run= onward, or restore cmdline.txt.bak.
One half of the panel is missing a colour Electrical, not software. HUB75 drives the halves on separate lines (R1/G1/B1 up, R2/G2/B2 down), so a fault confined to one half is a signal line, and rgb_sequence cannot cause it because it remaps both halves equally. On a Pi 3 A+, check the row above first — a fully seated Bonnet is by far the most likely cause and no amount of swapping parts will find it. Otherwise: reseat the ribbon at both ends (it seats about a millimetre further than feels right), then the panel's other connector, then a different ribbon, then the HAT. Change one thing at a time, and if four panels and three bonnets all fail identically, stop swapping parts: the constant is the Pi.
OSError: cannot open resource on fonts A permission error wearing a misleading message. The matrix library setuids to daemon after claiming GPIO, and Debian made home directories 0750 in Bookworm, so daemon cannot traverse /home/<user>. ./scoreboard doctor names the directories; the fix is sudo chmod o+x on each.
Many install steps fail at once Almost always one cause, not many. Either the boot-time apt timers held the dpkg lock, or a third-party repo apt cannot verify — on Trixie that fails every update, so git, pip and Pillow all go down with it. Re-run ./install.sh --yes; it now clears both before the package step.
make: No rule to make target 'build-python' Pre-v2.11 installer. Upstream moved the Python bindings to scikit-build-core and cmake in February 2026 and deleted that target. Update, or build by hand: sudo python3 -m pip install --break-system-packages ./matrix.
REMOTE HOST IDENTIFICATION HAS CHANGED after re-flashing Expected, not an attack. A fresh card generates new SSH host keys, and DHCP often hands the new board an address a previous one used, so your Mac compares the new key against the old board's entry. Clear it and reconnect: ssh-keygen -R <ip>, then ssh again and accept the new fingerprint. You will hit this on every re-flash and every clone, so it is worth knowing rather than worrying about.
You are debugging a board and nothing you change has any effect Check you are on the board you think you are. After a re-flash the new card usually lands on a different address while the old board is still powered on and still answering. grep -m1 VERSION ~/scoreboard/main.py and uptime -p settle it in two seconds: a version older than the zip you just installed, or an uptime measured in days, means you are on the previous unit.
Restart loop after changing a panel setting, panel dark Almost certainly parallel when you meant chain. They sit next to each other in the settings and mean different things: chain is panels wired one after another off a single output, which is what a second panel is; parallel is separate ribbons from separate GPIO banks, and the Adafruit HAT and Bonnet break out one HUB75 connector, so it can only ever be 1 on that hardware. Asking for 2 made the library call abort(), killing the process with SIGABRT before it printed anything to the panel, so systemd restarted it forever. From v2.19 the board corrects an impossible value, says so in the log, and runs. On an older build, set matrix.parallel back to 1 and restart.
Sunday shows yesterday’s college games instead of the NFL Fixed in v2.27. Both leagues arrive from ESPN in the same shape, so the rotation had no way to know that a finished Saturday game and a live Sunday one are not equally interesting, and the panel spent half its time on yesterday. The board now works out which day’s slate is current from the schedule — a game counts as today’s if it is live, or its kickoff falls on today in your timezone, which includes games that have not started, so an NFL Sunday is an NFL Sunday from midnight. Leagues with nothing today drop out of the rotation entirely, along with their poll pages and standings. Your own teams are the exception: a favourite’s last result still comes round, on one pass in three by default, because whether OSU won is still a question on Sunday morning. Both are adjustable under Today’s games only and My teams on their off day, and ./scoreboard status prints which slate the board thinks it is on. Deliberately not a day-of-week table: that needs an exception for Thanksgiving, for Friday college games, and for all of bowl and playoff season, and the exceptions are what break.
Two panels both locked to your team’s live game Different cause from the row below, same look. When a favourite is playing, the board stops rotating and camps on that game — correct on one panel, where the camped game is the entire playlist, but on a chained pair that one-screen playlist went to both cells. From v2.23 the favourite is pinned to the left cell and the rest of the slate keeps rotating on the right, so your game stays in one place and everything else moves beside it. With more cells, at least one always keeps rotating. Turn it off entirely with rotation.stay_on_live_favorite.
Two chained panels show the same game on both The board thinks it has one panel. HUB75 is a shift register with no back channel, so nothing on the Pi can detect how many panels are wired: the count has to be told to it once. When it is 1, the renderer draws a single 64×32 cell, the library clocks only 64 columns per row, and the second panel holds the same row data, which reads as a copy rather than as garbage. Fix it in the web UI under Daisy chained, or preseed it at card prep with --panels 2 so a two-panel unit is right the first time it lights up. The panel nearest the Pi is last in display order, so if the two games come up swapped, swap the ribbon between the panels rather than changing any setting.
Two boards fighting over one .local name A clone still carries the original's hostname, SSH host keys and machine-id. Give each one its own identity on its first boot, with the original powered off — phase 07 step 2.
Top half of the panel shows only blue, or one half is missing red and green, on a Pi 3 A+ The Bonnet is seated all the way down. A Pi 3 A+ has a metal shield over its wireless module directly under where the Bonnet sits, and full seating puts the Bonnet's underside against it, shorting out signal lines. Two data pins go and the rest survive, which reads exactly like a dead panel. Fit a 2×20 extra-tall stacking header (Adafruit 1979) so the Bonnet clears it, and put a strip of electrical tape over the shield. Lifting the Bonnet by hand proves the diagnosis but will not survive being carried anywhere. This is not software: it reproduces across panels, bonnets, ribbons, supplies and operating systems.
<name>.local does not resolve, but the board is up mDNS is not running. Use the IP instead: on the board, hostname -I, and whoami for the account name. Then check systemctl status avahi-daemon — if it is dead, sudo apt-get install -y avahi-daemon && sudo systemctl enable --now avahi-daemon. Worth fixing before a board leaves the house, because hostname access is the whole point of the handoff.
Logos with a single strong colour come out white or pink Pre-v2.14 bug, and it was two bugs stacked. The fetcher preferred ESPN's -dark asset, which for schools like Indiana, Alabama and Texas is the mark redrawn in flat white. Then a brightness boost measured luminance, which weights red at 30% and blue at 11%, so crimson scored about 69 of 255 with its red channel nearly full, got multiplied by 2.5, clipped red and lifted green and blue into pink. Any logo containing a white pixel was never boosted at all, which is why only some looked wrong. Update; the installer clears the cached bitmaps, which otherwise keep the old pictures forever.
A college team shows an NFL team’s logo Fixed in v2.21.1, and it affected every shared abbreviation: CIN is the Bengals and the Bearcats, MIA the Dolphins and the Hurricanes, HOU the Texans and the Cougars. The disk cache named files from the abbreviation and size alone, so both teams wrote CIN_20.png and whichever was fetched first owned it. Because the clash is on disk it survived restarts, while the in-memory cache was keyed correctly and hid it inside any single run. Cache files are now keyed on the source URL. Upgrading clears the cache automatically; to force it by hand, rm -rf ~/scoreboard/logo_cache and restart.
An NFL helmet renders as a coloured smudge Fixed in v2.21. The bundled helmets are hand-drawn at roughly 20×20 and stored as a 400×400 upscale, so every edge in them is a hard block boundary. The resize used LANCZOS, an interpolating filter meant for photographs, which averaged those blocks into one another: a five-colour helmet arrived as an orange blur. Pixel art is now sampled rather than filtered, decided by the source’s colour count, because the averaging is still right for everything else — the Ravens mark sampled the same way comes apart into specks. The same release also trims the painted-on margin those files carry, which had been surviving the resize and leaving every helmet smaller than the marks beside it.
A logo is on the panel but you cannot tell what it is Different from a mark that is too dark to see, and the reason it took two tries to fix. ESPN serves two versions of most logos — the real one and a -dark redraw for dark backgrounds — and neither is the right default. Preferring the redraw turned Indiana, Alabama and Texas white, because for those schools it is the mark in flat white. Preferring the real one unless it failed a legibility check was no better: the check asked for 3% of pixels lit, and Cincinnati’s Bearcats mark clears that at 4% while being invisible. From v2.25 both versions are rendered and measured, and the one that reads wins. The number scored is not how much of the mark is lit but how much is solid: Ohio State’s true-colour Block O measures 37% lit against 5% solid, a scarlet haze with no letter in it, where its redraw is 32% solid. True colour keeps a 10-point advantage, so a mark that already reads is never traded away for a marginal gain. python3 -m tools.logo_tune CIN --league ncaaf now prints which version the board chose and why.
One specific team's logo is a smudge at 20 px Some marks do not survive the shrink no matter the processing. Two options. Force the abbreviation in team colour by adding it to display.logo_text_teams in the web UI, which always reads. Or build better art: python3 -m tools.logo_tune OSU --league ncaaf writes a contact sheet of every treatment at panel size and magnified, then --pick N saves your choice to logos/ncaaf/OSU.png, which from then on wins over anything ESPN serves. Drop your own PNG in that folder and it works the same way.
A board has stopped picking up releases Start with ./scoreboard doctor, which now checks the whole chain and flags a check older than three days — a board that quietly stopped checking is a board that quietly stopped being fixable, and it will not announce it. The likely causes, in order: no key in /etc/scoreboard/ because the board was first installed from a release that predates this, fixed by re-running ./install.sh --yes; the recipient turned updates off; the timer is not enabled; or the version it is being offered is one that already failed here and is on the do-not-retry list, which state/update.log will say in as many words. Force a run with ./scoreboard selfupdate --force to see the whole sequence live.
A release went out and a board rolled itself back Working as intended, and the log says why. The updater tests a release in a staging directory before the live tree is touched, then requires the service to come back up and report the expected version on its own port; anything short of that restores the backup and records the version as bad so the board does not spend every night reinstalling it. Read state/update.log on that board, or look at the Updates section of its web page, which shows the same thing without ssh. Fix, bump the version, and publish again — boards will not retry the number that failed, so a re-release has to be a new version.
manifest signature does NOT verify in the update log The board is doing its job. Either the manifest was published without being signed, or it was signed with a different key than the one on that board. ./tools/release.sh signs on every run and verifies its own signature against the public key in the repo before publishing, so the usual cause is a key that was regenerated after the boards were built. There is no remote fix for that by design: replacing the key is a physical act, because a release that could replace the key could also replace the check.
Settings will not save, the config reverts, or the install half worked Suspect the card before anything else. A microSD does not fail cleanly: it starts returning bad data, ext4 remounts itself read-only to limit the damage, and from up here that looks like four separate bugs. ./scoreboard doctor checks this first now — read-only root, kernel I/O errors, recorded filesystem state, and whether the project directory actually accepts a write. If it flags any of them, copy config.json off and write a new card rather than debugging anything downstream.
Everything green, panel completely dark On a non-Adafruit board, the Pi's onboard sound driver holds the PWM peripheral the panel needs, and the library refuses to start rather than running badly. It says so on stderr, which for a service means the journal, so the install looks perfect. Fix: echo 'dtparam=audio=off' | sudo tee -a /boot/firmware/config.txt then reboot. ./scoreboard doctor now flags it.
Panel dark on a HAT that is not Adafruit's Wrong pin mapping. Sweep them: regular (most generic and clone boards, and hzeller's own reference wiring), adafruit-hat, adafruit-hat-pwm (Adafruit with the pin-4-to-18 jumper bridged), classic. Disable onboard audio first, or the two PWM mappings will refuse to run and you will wrongly rule them out.
The board reports a colour depth or slowdown it is not using Fixed in v2.26, and it was invisible from the outside, which is the interesting part. Each board model has a tuning profile — a Zero W is set to colour depth 8 and slowdown 0, the settings that keep it from flickering — and the web page's This board panel read those values back correctly. Nothing passed them to the panel. Frame rate, refresh cadence and logo prefetch all resolved through the profile properly; the two values that reach the matrix library were read straight from config.json with a hardcoded fallback behind them, so a board with those fields left blank ran the library's defaults of 11 and 1 while displaying 8 and 0. Mostly harmless on a Pi 3, whose profile matches the defaults anyway. On a Zero W it meant the one board that genuinely needs the lower settings was the one not getting them.
Panel shows random colours at power-on, like a scrambled channel For the first instant, expected. A HUB75 panel is a chain of shift registers with no reset line and no defined power-on state, so until the Pi has clocked a full frame into it the panel displays whatever the registers happened to come up holding. The board takes a few seconds to start, and that gap is what you are looking at. If it persists once the service is up, the first thing to check is matrix.gpio_slowdown, and to lower it rather than raise it. Clear the field entirely and let the board choose. A high slowdown pads every GPIO write, which stretches the refresh cycle until the panel is being redrawn too slowly to look like a picture — and because the setting sounds like a safety margin, it is the one people turn up when chasing flicker, which makes the display dramatically worse in a way that looks nothing like a settings problem. From v2.26 the board warns in the log when this value is above 2, and ./scoreboard doctor flags it. If it is already clear, reseat the HAT squarely.
Panel flickers or the brightness shimmers Four levers, and they are not equally good. In order: (1) Colour depth. This is the flicker setting. Each bit you drop roughly halves the time a frame takes, so 8 or 9 instead of 11 buys a large refresh increase and costs you banding in gradients, which a scoreboard drawing flat colours and text does not have. (2) Reserve a core. On any quad-core Pi, append isolcpus=3 to the single line in /boot/firmware/cmdline.txt and reboot. The refresh runs in a thread that has to hit its timing or the panel dims and shimmers; this gives it a core nothing else can touch. The library's author recommends it outright. (3) The hardware mod. On an Adafruit HAT or Bonnet in its default wiring, the output-enable line sits on GPIO 4, which is not a hardware-PWM pin, so the library toggles it in software. Its own documentation is blunt about the consequence: random brightness glitches. One wire between GPIO 4 and GPIO 18 (the Bonnet has a solder pad for it) moves it onto the PWM hardware. Then set Wiring to Adafruit HAT, PWM mod and add dtparam=audio=off to /boot/firmware/config.txt, because GPIO 18 is also the onboard audio pin and the library refuses to start while the sound driver holds it. This is the actual fix. The other three are working around not having done it. (4) GPIO slowdown: leave it alone. It is the obvious-looking knob and it is the wrong one, for the reasons in the row above. ./scoreboard doctor now checks 2, 3 and 4 for you.
Flicker in a regular pulse, about once a minute Different problem with a different cause: something else on the Pi is stealing the refresh thread's timing on a schedule. The library's docs name the usual suspects, and they are mundane — an NTP adjustment, a cron job, even top left running in another window produces a faint tick every time it redraws. Constant shimmer is a refresh-rate problem and belongs to the row above; a rhythm points at another process. Reserving a core with isolcpus=3 is the fix that addresses both, since it removes the contention rather than the contender.
